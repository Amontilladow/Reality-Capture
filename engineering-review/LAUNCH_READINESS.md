# Launch Readiness — EngineeringOS Reality Capture

Produced by a launch-readiness sprint and updated by three follow-on
sprints (two corrective-blockers sprints, plus a final validation sprint).
This is a status report, not a go-ahead. Every row below is backed by either
a command that was actually run, direct source inspection, or an explicitly
marked BLOCKED item — nothing here is a guess. See `MOBILE_STORE_READINESS.md`
for the store-submission checklist and the final sprint report (delivered in
chat) for the full verification log and file-change list.

## Launch level definitions

- **Internal pilot** — a handful of the product team's own accounts, on a
  private/staging environment, used to shake out obvious breakage before any
  outside user sees it. Tolerates known rough edges as long as they're
  documented and don't lose data or leak across tenants.
- **Private beta** — a limited set of real, external customer accounts, on
  production infrastructure, under an NDA/agreement rather than public
  self-signup. Requires the security/tenancy/data-safety basics to actually
  hold, but can tolerate incomplete polish, missing store listings, and
  manual onboarding.
- **Public launch** — open self-signup, public app store listings, no
  hand-holding. Requires every critical blocker below to be closed — store
  assets, legal/privacy materials, monitoring, and backup/restore included.

## Readiness table

| Area | Status | Evidence | Blocker action |
|---|---|---|---|
| Web build | PASS | `pnpm --filter web build` succeeds (see verification log) | None |
| API startup | PASS | `pnpm --filter api exec tsc --noEmit` clean; API boots against local Postgres/Redis and serves all routes (`Nest application successfully started`) | None |
| Authentication | Implemented, partially verified | Login/refresh/logout/forgot/reset/accept-invitation endpoints exist and were exercised live (login, JWT issuance) this sprint; throttler (`auth` bucket, 10/min) is registered globally | Rate-limit behavior under real concurrent load, and forgot/reset email delivery, were not exercised live (no SMTP configured in this sandbox) |
| Tenant isolation | Implemented, partially verified | `withTenant`-scoped queries used consistently in services inspected this sprint and prior sprints; DTO whitelisting confirmed live (`property address should not exist` rejection observed against `/projects`) | Postgres RLS relies on the `app_user` role, but production's actual `DB_USER` (Render-managed, table owner) bypasses RLS by ownership — documented at length in `CURRENT_STATUS.md`. This is a real, unresolved gap: today, tenant isolation in production rests entirely on the application code's own `WHERE company_id = ...` discipline, not on a database-enforced backstop. |
| Database migrations | Implemented, partially verified | All 48 migrations in `apps/api/src/database/migrations` applied cleanly against a fresh local database this sprint (`node run-migrations.ts`, tracked via `_migrations`); Render's `preDeployCommand` runs this before traffic per `render.yaml` | Rollback story is "re-deploy a prior image," not a scripted down-migration — acceptable for a pre-launch product but should be stated explicitly to whoever is on call |
| Restricted production DB role | BLOCKED (documented, not fixed) | `app_user` role exists with no password, no grants, and `rolbypassrls` not confirmed `false` (migration 001); production connects via Render's own superuser/table-owner credential instead, which bypasses RLS by ownership regardless of `app_user`'s configuration | Requires an owner/infra decision, not a code change: give `app_user` a real password and explicit grants, set `rolbypassrls = false`, point production's `DB_USER` at it instead of the table-owner credential, and verify RLS actually filters rows under that role before trusting it — this is deliberately out of scope for a "small, reviewable" sprint change |
| Object storage | Implemented, verified — completed across three sprints | **Transport-level enforcement**: presigned PUT URLs have no `Content-Length-Range` condition mechanism (only presigned POST supports that), so no upload in this codebase is size-constrained at the signature itself; that remains a deployment/provider-level task (switching to presigned POST would change every upload caller's request shape — too broad for a corrective sprint). **Server-side post-upload enforcement** (the real fix, now complete): `StorageService.getObjectSize()`/`deleteIfExists()` are called at the one server-controlled persistence point for every upload family that has one, verifying the *actual* stored object's size — never the client-declared one — before any DB row is created, any quota is counted, or any processing is queued: captures, BIM/IFC models, drawings, internal documents (external/metadata-only documents are correctly left unverified — they have no object of ours to check), issue view-state screenshots, issue/RFI/snag attachments, project/organization branding logos, and (found and fixed in the final validation sprint) workforce screenshots. That last one was a real, reproducible gap found by tracing every `getUploadUrl()` caller in the codebase (not just the originally-named families): `ScreenshotsService.record()` inserted the DB row directly from a client-supplied `storageKey`, with no check that the key actually belonged to the calling user/company's own upload namespace and no verification that the object was ever uploaded or how large it was — a caller could record an arbitrary storage key (including another company's) or an oversized/nonexistent object. Fixed with the same pattern used everywhere else: reject a `storageKey` outside `${companyId}/workforce-screenshots/${userId}/`, verify the real object exists and is ≤10MB via `getObjectSize()`, and `deleteIfExists()` on rejection. 5 new/updated tests cover the namespace check, the missing-object case, and the oversized-with-cleanup case (`screenshots.service.spec.ts`, 12/12 passing). All 273 API tests pass overall. | None remaining for declared-vs-actual size enforcement across any upload family found in the codebase. True transport-level (presigned-POST signature) enforcement is still not implemented — see the transport-level note — but is a provider/deployment decision, not a blocking gap in the application's own logic. |
| Redis / queue | Implemented, partially verified | Bull queues (`image-processing`, IFC processing) configured with bounded retries + exponential backoff (`attempts: 3`, `backoff: exponential`) — confirmed via source this sprint | No API/admin visibility into failed jobs was found (no endpoint or dashboard surfaces `queue.getFailed()`); a stuck/failed job is currently only discoverable via direct Redis/Bull inspection, not through the product |
| IFC processing | Implemented, verified (with a nuance) | `ifc-processing.processor.ts` explicitly distinguishes `SUCCESS`/`PARTIAL`/`FAILED` in its saved processing report, based on `elementsSkipped`, and does not throw the job away on a partial result — it does **not** silently report full success when elements are skipped | The underlying BIM model record's own `status` column is set to `'ready'` in both the SUCCESS and PARTIAL cases — the SUCCESS/PARTIAL distinction lives only in the separately-saved processing report, not in the primary status field a model-list UI would most likely read. Whether the frontend actually surfaces this distinction to the user was not verified this sprint. |
| BIM viewer | Not independently re-verified this sprint | Prior sprints (`BIM_VIEWER_GAP_ANALYSIS.md`, `ROOT_CAUSE_REPORT_BIM_VIEWER.md`) document known viewer issues in detail | Do not claim BIM viewer readiness beyond what those existing documents state; this sprint did not load a real IFC model through the viewer (no seeded BIM model existed, and generating one needs a real IFC file + working `apps/ifc-service` pipeline, which was out of scope to stand up here) |
| Browser compatibility | Verified — full 6-viewport × 13-route matrix, Chromium only | The final validation sprint ran the most exhaustive pass to date: 6 viewports (desktop 1440×900, laptop 1280×800, tablet landscape 1024×768, tablet portrait 768×1024, phone-large 390×844, phone-small 360×800) × 13 routes (Login + Project list, Messages, Workforce, Project detail, Captures, Drawings, BuildLens, BIM models, Issues, RFIs, Snagging, Reports) = 78 live combinations against a real running API+web+Postgres+Redis stack with an authenticated session. 77/78 showed zero horizontal overflow. The one failure — RFIs page at 360×800 (`scrollWidth: 364` vs viewport `360`) — was reproduced, root-caused (the date-range filter's two native `<input type="date">` elements plus their "to" label, inside a `flex items-center` row with no `flex-wrap` of its own, couldn't shrink below their combined intrinsic width), fixed with a one-line change (`RfisPage.tsx`: added `flex-wrap` to that inner row so the second date input wraps instead of forcing overflow), and re-verified live at all 6 viewports afterward — `scrollWidth === viewportWidth` everywhere, including 360×800. A separate transient-404/console-error signal seen during the first exhaustive run was investigated and root-caused as a test-harness artifact (the API's own `ThrottlerModule` 100-req/60s bucket being exhausted by the test script's own rapid-fire requests across 78 combinations in one run), confirmed via direct `curl` (429, not a real 404) and a slower re-run (zero errors) — not a product defect. | Only Chromium was exercised — no Firefox or WebKit binaries exist in this sandbox (only `chromium`, `chromium_headless_shell`, and `ffmpeg` are installed under the Playwright browsers path), so cross-browser (Firefox/WebKit/Safari) compatibility remains **BLOCKED**, not verified, and no claim is made about it. The BIM/360 viewers were reached (routes load) but not exercised with real model/capture data or WebGL-rendering verification. |
| Mobile Android | Implemented, not device-tested | Offline-first capture/sync (SQLite queue, serial upload, bounded retries via the newly-wired idempotent `/captures/sync` endpoint), permission handling, and background sync all verified via source + `tsc --noEmit`. The final validation sprint directly confirmed (not inferred) that Android device/emulator testing is architecturally impossible in this sandbox: `adb version`, `which emulator`, `which scrcpy`, `which maestro`, and `which detox` all failed — none of these binaries exist here. **BLOCKED, not PASS.** Also newly observed this sprint: `app.json`'s explicit `android.permissions` array lists `CAMERA`, `RECORD_AUDIO`, `ACCESS_COARSE_LOCATION`, and `ACCESS_FINE_LOCATION` a second time, duplicating what the `expo-camera`/`expo-location` config plugins already add to the resolved config automatically. Left unfixed: Android's manifest merger de-dupes identical `<uses-permission>` tags, so this is very likely harmless, and removing entries by hand risks fighting the plugin-managed config on a future SDK upgrade — a cosmetic cleanup, not a functional defect, and out of scope for a "small, targeted" fix. | Legacy storage permissions should be reviewed against current Android 13+ scoped-storage policy (see `MOBILE_STORE_READINESS.md`); real Android device/emulator testing requires a macOS/Linux host with the Android SDK platform-tools and an emulator image installed — neither exists in this environment. |
| Mobile iOS/iPad | Implemented, not device-tested | Same offline/permission/sync logic is platform-agnostic (Expo); `app.json` declares `supportsTablet: true` and all iOS usage-description strings. **Correction (still holds)**: a prior pass of this document reported `NSMicrophoneUsageDescription` missing based on grepping `infoPlist` directly; re-verified again this sprint against the installed `expo-camera` plugin's own source and `npx expo config --type public`'s resolved output, which both confirm the string is present via `app.json`'s `microphonePermission` field. This sprint also directly confirmed (not inferred) that iOS device/simulator testing is architecturally impossible here: `xcrun`, `xcodebuild`, and any Xcode installation require macOS, and `uname -a` confirms this sandbox is Linux (`Linux vm 6.18.44-fc-v50`). **BLOCKED, not PASS — and not merely "no device available," but categorically impossible on this host.** | No physical-device or simulator test was performed, and none can be performed in this sandbox at all — iOS testing requires a real macOS host with Xcode. The still-missing app icon (see `MOBILE_STORE_READINESS.md`) would very likely fail an actual `eas build` before it got anywhere near a device or App Store review — this was not attempted live in this sandbox (no EAS credentials), so it's a strong inference from the missing file, not a confirmed build failure. |
| Offline sync | Implemented, verified via source + one live fix | Capture-before-upload, app-restart survival (SQLite persistence), bounded retries (`MAX_UPLOAD_RETRIES = 5`), visible per-item retry UI (`SyncStatusScreen.tsx`), and 401→refresh→retry auth handling all confirmed by reading the actual code paths. This sprint found and fixed a real duplicate-upload risk: the mobile app was calling a plain, non-idempotent register endpoint, so a retry after an ambiguous failure (e.g. the app killed between the storage PUT succeeding and the register call completing) could create a second capture. Fixed by wiring the app to the already-built-but-unused idempotent `POST /captures/sync` batch endpoint, with a passing new backend test (`captures.service.spec.ts`, 3/3 tests). | Not tested under an actual interrupted/degraded network condition on a real device — this is a source-level guarantee, not an on-device observation |
| Monitoring | Partially implemented — improved this sprint | `/health` (Render's actual `healthCheckPath`, gating deploys/restarts) is **unchanged on purpose** — still just a DB ping, so a transient Redis/storage blip can't get a healthy instance killed. **New**: `/health/ready` checks database, Redis (via the existing Bull-managed connection, no new connection opened), and object storage (a cheap `HeadBucketCommand`, no credentials or object data exposed) independently, reporting each dependency's status separately rather than collapsing to one pass/fail. Verified live against a real local Postgres+Redis stack with object storage deliberately down: `/health` correctly stayed `{"status":"ok"}` while `/health/ready` correctly reported `{"status":"degraded","services":{"database":"ok","redis":"ok","objectStorage":"error"}}`. 7 passing unit tests (`health.controller.spec.ts`) cover each dependency failing independently and together. IFC worker, AI service, and Qdrant reachability are still not checked by either endpoint. No mobile crash reporting (Sentry/Crashlytics) exists. | `/health/ready` is not wired into Render's deploy/restart gate — that's a deliberate choice (see the code comment), not an oversight: promoting it there is a real production-behavior change needing its own decision once there's an actual on-call/monitoring process to back it. Before private beta: stand up something that actually polls `/health/ready` and alerts (this endpoint existing is necessary but not sufficient). Before public launch: add mobile crash reporting, and consider extending readiness to the IFC worker/AI service/Qdrant. |
| Backups / restore | Not verified this sprint | No backup/restore procedure or script was found in the repository; Render's managed Postgres offering typically includes automated backups, but this was not confirmed against the actual production database configuration | **Needs owner decision/verification**: confirm what backup retention Render is actually configured with for the production database, and document (even briefly) how a restore would be performed, before accepting real customer data in a private beta |
| Privacy / legal materials | Not present | No privacy policy, terms of service, or data-processing documentation exists in the repository | Required before public launch (and arguably before private beta, if beta customers are real companies under any kind of agreement); this is legal/business work, not something this sprint could draft credibly from source code alone |
| Support process | Not defined | No support contact, escalation path, or incident-response process was found or created | Needs owner decision before any external user (pilot or beta) is given access |

## Executive verdict

| Target | Verdict |
|---|---|
| Web SaaS — internal pilot | **READY WITH CONDITIONS** — core auth/tenancy/upload paths work and were exercised live; conditions: accept the known RLS-bypass-by-role gap as an internal-only risk, and know that `/health` (still) won't tell you about a Redis/storage outage — use the new `/health/ready` for that if you're watching manually. |
| Web SaaS — private beta | **NOT READY** — the DB-role RLS gap and the absence of any confirmed backup/restore process are real risks once real external customer data is involved. (Storage-layer size enforcement — previously the third item in this row — is now real across every upload family with a safe completion point; see the Object storage row. That gap is fully closed and no longer a private-beta blocker on its own.) |
| Web SaaS — public launch | **NOT READY** — all private-beta blockers apply, plus no privacy/legal materials and no confirmed backup/restore process. Monitoring has a real readiness signal now (`/health/ready`) but nothing is wired up to poll or alert on it yet. |
| Android — internal testing | **READY WITH CONDITIONS** — installable via a development/internal EAS build once one is actually produced (not done this sprint — no store credentials, none requested); offline/permission logic is sound by source inspection but untested on a real device. |
| Android — public store release | **NOT READY** — no app icon/store assets exist, storage permissions need a currency review, and no store listing/signing has been set up. |
| iOS — TestFlight | **BLOCKED** — not by the microphone string (re-verified present and correct this sprint — see the Mobile iOS/iPad row), but the missing app icon (`MOBILE_STORE_READINESS.md`) would very likely fail an actual `eas build` before a TestFlight submission is even possible; this wasn't attempted live (no EAS credentials in this sandbox), so treat it as a strong inference, not a confirmed failure. |
| iOS — App Store release | **NOT READY** — TestFlight blocker applies, plus the same missing store assets and undefined release-ops items as Android. |
| Desktop browser support | **READY WITH CONDITIONS** — verified across the full 6-viewport × 13-route matrix (desktop 1440×900 and laptop 1280×800 both included) with zero layout issues after the RFI-page fix; Chromium only, Firefox/WebKit not available in this sandbox (BLOCKED, not tested). |
| Tablet browser support | **READY WITH CONDITIONS** — verified at both tablet landscape (1024×768) and tablet portrait (768×1024) across all 13 routes, zero overflow found; Chromium only. |
| Mobile browser support | **READY WITH CONDITIONS** — verified at both phone-large (390×844) and phone-small (360×800) across all 13 routes; found and fixed the one real overflow bug this sprint surfaced (RFIs page at 360×800); zero overflow across all 78 combinations after the fix; Chromium only. |
| Native phone support | **BLOCKED** — same source-level basis as the Android/iOS rows above, but this sprint upgraded the verdict from "no device was available" to a directly-confirmed, categorical BLOCKED: no `adb`, no Android emulator, and no Xcode/`xcrun` toolchain (Linux host) exist in this sandbox, so no physical-device or emulator/simulator test of any kind can be run here. |
| Native tablet support | **BLOCKED (device testing) / NOT DECLARED (Android tablet layout policy)** — iOS declares `supportsTablet: true` with no tablet-specific layout beyond the phone UI scaling up; Android has no explicit tablet declaration in `app.json` and no tablet-specific layout was found — if phone-only is the intent for Android, that should be stated as policy rather than left implicit. Device/simulator testing is BLOCKED for the same reason as Native phone support. |

No row above claims public-launch readiness, and none should be read that
way — every "READY WITH CONDITIONS" verdict names its condition explicitly,
and every BLOCKED verdict reflects a directly-confirmed missing resource,
never a guess.
